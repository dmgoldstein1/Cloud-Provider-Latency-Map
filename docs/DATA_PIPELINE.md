# Data Pipeline & Dashboard Integration Guide

This document describes how the latency measurement data is produced, where it is
stored, and exactly how to wire new measurements into the static web dashboard.
Read it fully before modifying anything.

---

## 1. High-level data flow

```
scripts/netlat.sh (provisions VMs, pings, collects, aggregates)
      |
      v
scripts/runs/run-<RUN_ID>/            per-run outputs (CSV matrices + raw pings)
      |
      |  scripts/stitch.py (merge chunked runs when the 30-VM cap splits a run)
      v
scripts/runs/stitched/                combined 33x33 matrices
      |
      |  conversion (see §5) -> data/locations_synthetic.json
      v
data/data.js                          generated bundle (VML_DATA.synthetic)
      |
      v
index.html -> js/normalize.js -> js/app.js (dashboard renders it)
```

Key rule: **the dashboard never talks to the network.** It is a static page that
must work from `file://`. All data is inlined into `data/data.js` by
`scripts/build_data_js.py`. If you change any `data/*.json`, re-run that script.

---

## 2. Measurement output: `scripts/runs/run-<RUN_ID>/`

Each `./scripts/netlat.sh` run creates one directory. Every instance is torn down
after the run (use `--keep` to leave VMs up). A run dir contains:

| File | Meaning |
|---|---|
| `instances.tsv` | `region<TAB>instance_id<TAB>ip<TAB>plan<TAB>state` — one line per live host |
| `peers.txt` | newline-separated IPs of all confirmed hosts (input to the worker) |
| `measure.py` | the ping worker that ran on each VM (source of truth for metrics) |
| `aggregate.py` | turns `raw/*.csv` into the `*_matrix.csv` files |
| `raw/<region>.csv` | per-source raw results, **one row per destination IP** |
| `latency_matrix.csv` | square matrix, ms — `avg` per src→dst |
| `jitter_matrix.csv` | square matrix, ms — `jitter` per src→dst |
| `loss_matrix.csv` | square matrix, % — `loss_pct` per src→dst |
| `manifest.json` | `{regions: {code: {id, ip, plan, state}}, status}` |
| `status_snapshot.json` | status.vultr.com feed captured at run start |
| `at_risk.txt` | region codes with ongoing alerts (advisory only) |

### `raw/<region>.csv` format
Columns: `dst,min,avg,max,stddev,jitter,loss_pct,sent,received`
- `dst` is a **raw IP**, not a region code. Map IP→region via `instances.tsv`.
- `avg` is mean RTT in ms; `jitter` is mean absolute inter-packet delta in ms.
- A missing/zero-length row means that host never finished (SSH died) — the
  cell is blank in the matrix, not `0`.

### `*_matrix.csv` format
Header row: `src,<dst-region>,<dst-region>,...` — one column per region, in
`instances.tsv` order. Each data row is `src-region,<ms>,<ms>,...`.
Diagonal (self) cells are ~0.05ms (the VM pinging itself), not 0.

## 3. Stitching chunked runs: `scripts/stitch.py`

The Vultr account is capped at **30 active instances**, but there are 33 regions.
A single run therefore always misses a few regions. We run overlapping chunks and
merge them:

```
python3 scripts/stitch.py scripts/runs/stitched \
  scripts/runs/run-<A> scripts/runs/run-<B> scripts/runs/run-<C>
```

- Merges `latency/jitter/loss_matrix.csv` from every listed run into one set of
  33x33 matrices under `scripts/runs/stitched/`.
- **Later run dirs win** on overlapping cells (keeps newest measurements).
- Writes `manifest.json` with `{regions: [...], runs, coverage, note}` and prints
  coverage like `wrote .../latency_matrix.csv (1089/1089 cells)`.
- `1089 = 33×33`. If coverage is less, some region was never confirmed in any run.

Currently the merged full dataset is `scripts/runs/stitched/` (1089/1089 cells).

## 4. Dashboard data contract: `data/data.js`

`index.html` loads these scripts in order:

```
lib/d3.v7.min.js, lib/topojson-client.min.js, lib/d3-scale-chromatic.min.js
data/data.js                    <- ALL data lives here (globals, no fetch)
js/config.js                    <- metric definitions + defaults
js/normalize.js                 <- converts VML_DATA.synthetic -> matrices
js/map.js, js/charts.js, js/app.js
```

`data/data.js` is generated by `scripts/build_data_js.py`, which inlines three
JSON files into `window.VML_DATA`:

| data.js property | Source file | Contents |
|---|---|---|
| `VML_DATA.synthetic` | `data/locations_synthetic.json` | **the measured/synthetic metric data** |
| `VML_DATA.regions` | `data/regions.json` | region metadata: code, name, lat/lon, continent |
| `VML_DATA.world` | `data/countries-110m.json` | world topojson for the map |

Rebuild after touching any of them:

```
python3 scripts/build_data_js.py
```

### `locations_synthetic.json` schema (this is what the dashboard consumes)
```json
{
  "source": "https://status.vultr.com/status.json",
  "retrieved_at": "2026-08-08",
  "regions": [
    {
      "code": "ams",
      "location": "Amsterdam",
      "country": "NL",
      "country_name": "Netherlands",
      "latency": { "atl": 113, "blr": 113, "ord": 112, "...": 0 },
      "jitter":   { "atl": 1.7, "blr": 6.3, "ord": 2.2, "...": 0 }
    }
  ]
}
```
- Exactly one object per region; `code` must match keys in `regions.json`.
- `latency`/`jitter` are maps of **dst-region-code → value**. Values are rounded
  to 1 decimal in the current file but any float works.
- Every region key must appear in every region's `latency`/`jitter` map, or the
  matrix gets `0` for the missing cell (see `normalize.js` `build()`).
- **No `loss` field today.** The dashboard only knows `latency` and `jitter`
  (see `js/config.js` `metrics`). To surface loss you must also edit
  `config.js`, `normalize.js`, and the metric button group in `index.html`.

### `normalize.js` behavior (read before converting)
`fromVultrStatus(raw)` builds square matrices:
- `order` = region codes in file order.
- `values[i][j]` = `region[i].latency[order[j]]` (or jitter), `0` if absent.
- `loadDataset()` calls it on `window.VML_DATA.synthetic`.

So the conversion from CSVs to `synthetic` is: for each src region, read its row
of `latency_matrix.csv` and emit `{code, location, country, country_name,
latency: {dst: avg}, jitter: {dst: jitter}}`, skipping the `src` column and blank
cells.

## 5. How to incorporate new measurements (step by step)

1. **Locate the data.** Fresh full matrix: `scripts/runs/stitched/`. A single
   run's own matrix also works if you only want that subset.
2. **Convert matrices → `data/locations_synthetic.json`.** Write a small script
   (or inline python) that reads `scripts/runs/stitched/{latency,jitter}_matrix.csv`
   plus `scripts/regions.json`/`data/regions.json` for `location`/`country` and
   emits the schema above. There is **no existing converter** — you must write it
   (it belongs in `scripts/`, e.g. `scripts/convert_stitched_to_synthetic.py`).
   Round values to 1 decimal to match existing style. Fill every cell (33 regions
   × 33 destinations per metric).
3. **Set provenance.** Update `"source"` (e.g. `"measured via netlat.sh"`) and
   `"retrieved_at"` (today's date) in `locations_synthetic.json`.
4. **Rebuild the bundle:** `python3 scripts/build_data_js.py`
5. **Verify:** open `index.html` (double-click works; it's `file://`-safe).
   - Header should still say `33 regions`.
   - Confirm the matrix is populated and values match the CSVs (spot-check a few
     pairs, e.g. the tooltip on an arc, or the heatmap cell).
6. **(Optional) point `data/netlat/latest` at the run:** `./scripts/import_run.sh`
   creates `data/netlat/latest -> scripts/runs/run-<id>`. Useful as a stable
   pointer for follow-up automation.
7. **(Optional) surface loss:** add `loss` to `js/config.js` `metrics`, teach
   `normalize.js` to build it, add a `data-loss` metric button in `index.html`.
   The CSV already has the data; only the dashboard layer is missing it.

### Coordinate/name matching caveat
`regions.json` is the authoritative list of the 33 regions with lat/lon/continent.
When converting, derive `location`/`country`/`country_name` from `regions.json`,
NOT from the CSV (CSVs only carry region codes).

## 6. Gotchas & operational notes

- **30-instance cap:** never expect a single `netlat.sh` run to cover all 33
  regions. Use `--regions <csv>` for chunked runs and `stitch.py` to merge.
- **atl/ewr plan bug (fixed):** plan selection must require `ram >= 1024`
  (`select(.ram >= 1024)`) or Ubuntu 26.04 rejects 0.5GB plans. Don't "fix" the
  jq filter back.
- **measure.py self-ping:** diagonal is ~0.05ms, not 0 — don't treat it as a gap.
- **Blank cells** mean "no data", never 0. `normalize.js` currently converts
  missing to `0`; consider guarding against that when converting CSVs.
- **data.js inlines JSON verbatim.** Keep the `(function(){...})()` wrapper that
  `build_data_js.py` writes; don't hand-edit `data/data.js`.
- Two copies of `locations_synthetic.json` exist (`data/` and `scripts/`) and are
  currently identical. `build_data_js.py` reads the one in **`data/`**. The
  `scripts/` copy is the placeholder the dashboard was seeded with. Keep them in
  sync or move the canonical one into `data/` and update any references.
- All instances are billed by the hour and torn down automatically. If you see
  leftover `netlat-*` VMs, delete them via the API or the dashboard won't be the
  only thing draining the account.
